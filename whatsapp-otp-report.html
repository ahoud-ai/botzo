١ — تحليل جاهزية النظام الحالي

الخلاصة الفورية: النظام في حالة ممتازة. البنية التحتية الكاملة لإرسال WhatsApp OTP موجودة بالفعل ومستخدمة في الإنتاج. نسبة الجاهزية ~80% — ما تبقى هو ربط وإعداد، ليس بناء.

١.٢ — هل طريقة الإرسال الحالية مناسبة لـ OTP؟

نعم، بشرط تعديل واحد مهم: sendTemplateMessage() تعمل مباشرة وبشكل متزامن (synchronous) في بعض أجزاء النظام — لـ OTP نحتاجها تعمل عبر Queue أولاً لضمان السرعة وعدم تأثر تجربة المستخدم.

الطريقة المطلوبة للـ OTP

Request → Queue 'otp' (أعلى أولوية) → Worker → إرسال

التعديلالحجمالوصف

٤ — استخدام WhatsApp Infrastructure الحالية

٤.١ — هل نستخدم حساب العملاء أم حساباً منفصلاً؟

السؤال الجوهري: Botzo تخدم شركات كل واحدة منها رقم WhatsApp خاص بها مخزن في المنصة. OTP الخاص بـ Botzo (للمستخدمين الجدد المسجلين في المنصة) يجب أن يُرسَل من رقم Botzo الرسمي كمنصة — وليس من أرقام العملاء.

❌ الخيار الخاطئ: أرقام العملاء

  • مشكلة قانونية وأخلاقية: رقم شركة أخرى
  • إذا عاقب Meta رقم عميل → يتأثر OTP
  • ربك في credentials عملاء
  • مخالف لشروط WhatsApp

✅ الخيار الصحيح: رقم Botzo المنفصل

  • رقم هاتف مخصص لـ Botzo كمنصة
  • WABA خاصة بـ Botzo (أو نفس WABA + رقم جديد)
  • Credentials تُخزَّن في Settings table
  • معزول تماماً عن حسابات العملاء
  • إذا حدثت مشكلة → تؤثر على OTP فقط، لا الحملات

٤.٢ — كيف يتم الربط تقنياً

النظام الحالي يبني WhatsappService لكل عميل بـ credentials خاصة به. للـ OTP نضيف BotzoSystemWhatsAppService — wrapper بسيط يبني نفس الـ Service لكن بـ credentials Botzo المخزنة في Settings table. لا يُلمس كود الإرسال الأصلي.

// المبدأ البسيط: // بدلاً من: Organization credentials → WhatsappService // نضيف: Botzo System credentials → BotzoSystemWhatsAppService → WhatsappService // // نفس المحرك، credentials مختلفة، نتيجة واحدة: رسالة WhatsApp تصل

٤.٣ — ما يحتاجه إعداد Botzo System Account

  • ١
    رقم هاتف جديد غير مسجل على WhatsApp — يصبح رقم Botzo الرسمي لإرسال أكواد التحقق.
  • ٢
    WhatsApp Business Account (WABA) — يمكن أن تكون نفس WABA الموجودة أو WABA جديدة مخصصة للنظام.
  • ٣
    إعداد Credentials في Settings — نفس طريقة mail_config الموجودة: access_token, phone_number_id, waba_id تُخزَّن في جدول Settings مشفرة.
  • ٤
    Authentication Template معتمد من Meta — يُقدَّم مرة واحدة ويُعاد استخدامه لكل عمليات OTP.

٥ — التوافق مع سياسات Meta

٥.١ — لماذا Authentication Template وليس غيره؟

WhatsApp يقسّم القوالب لثلاثة أنواع. اختيار النوع الخاطئ يعني رفض Template أو تعطيل الخدمة:

النوعالغرضمناسب لـ OTP؟
MARKETING 🔴 العروض والإعلانات التجارية ✗ غير مسموح لـ OTP
UTILITY 🟡 تحديثات الطلبات، التذكيرات ⚠ مقبول لكن غير مثالي
AUTHENTICATION 🟢 رموز التحقق وتسجيل الدخول ✓ الخيار الصح
ميزة AUTHENTICATION الأهم: رسائل التحقق (Authentication) لا تخضع لـ قاعدة الـ 24 ساعة التي تقيّد رسائل MARKETING. يمكن إرسالها في أي وقت لأي مستخدم سواء تواصل معك أم لا — وهذا بالضبط ما نحتاجه لـ OTP.

٥.٢ — قواعد Authentication Templates الإلزامية

  • ✓
    محتوى التحقق فقط — ممنوع أي محتوى تسويقي أو روابط خارجية في رسائل AUTHENTICATION. الرسالة يجب أن تحتوي فقط الكود وتعليمات استخدامه.
  • ✓
    عبارة الأمان إلزامية — يجب تضمين عبارة "لا تشاركها مع أحد" أو "Do not share this code" — Meta تطلبها صراحةً.
  • ✓
    زر OTP — يُفضَّل إضافة زر COPY_CODE لتسهيل نسخ الكود للمستخدم. Meta تدعمه وتُشجع عليه.
  • ✓
    انتهاء صلاحية — يُستحسن ذكر مدة صلاحية الكود (15 دقيقة) — يزيد ثقة المستخدم ومصداقية الرسالة.

٨.١ — المبادئ الأساسية للتصميم

  • ١
    لا تكسر ما يعمل

    قناة واحدة، محرك واحد

  • ٣
    الأولوية في Queue حل معظم المشاكل
    إضافة 'otp' قبل 'default' في worker config — تعديل من سطر واحد يضمن أن OTP يُعالج دائماً قبل أي شيء آخر.
  • ٤
    العزل الكامل للأرقام
    رقم Botzo System لـ OTP فقط. رقم العملاء للحملات فقط. لا يختلطان أبداً.
