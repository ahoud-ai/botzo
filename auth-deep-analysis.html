٤ — Phone Number Uniqueness & Normalization

٤.١ — الوضع الحالي

حقل phone موجود في users table كـ nullable بدون أي unique constraint. يمكن لمستخدمين متعددين أن يسجلوا بنفس رقم الهاتف. الـ E.164 normalization موجود في UserService عبر phone() helper لكن فقط عند التخزين — لا validation قبله.

٤.٢ — Normalization Strategy

// المشكلة: نفس الرقم بصيغ مختلفة "0501234567" // Saudi local format "966501234567" // Without + prefix "+966501234567" // E.164 ✓ "05-012-34567" // With separators " +966 501 234 567 " // With spaces // الحل: Normalize BEFORE storing + BEFORE lookup // UserService already uses phone() helper — extend it: private function normalizePhone(string $raw): string { // Step 1: Strip all non-digit non-plus chars $cleaned = preg_replace('/[^\d+]/', '', trim($raw)); // Step 2: Use existing phone() helper for E.164 // The phone() helper (likely uses brick/phonenumber) handles: // - Country code detection // - Leading zero removal // - E.164 formatting (+966501234567) return phone($cleaned)->formatE164(); }

٤.٣ — Database Constraint Strategy

تحدي Soft Deletes: MySQL يعامل NULL كقيمة فريدة في UNIQUE indexes — أي أن (phone='+966x', deleted_at=NULL) يمكن أن يظهر مرة واحدة فقط للمستخدمين النشطين. هذا يتطابق مع النهج الحالي للـ email unique constraint.
-- Migration 1: إضافة phone_verified_at + unique constraint Schema::table('users', function (Blueprint $table) { $table->timestamp('phone_verified_at') ->nullable() ->after('email_verified_at'); // Composite unique: allows soft-deleted duplicate phones // NULL != NULL in MySQL unique index → only one active user per phone $table->unique( ['phone', 'deleted_at'], 'users_phone_active_unique' ); // Fast lookup during phone login $table->index('phone', 'idx_users_phone'); });

٨ — Security Architecture

٨.١ — Session vs JWT — القرار

القرار: ابقَ على Sessions. النظام الحالي يعتمد على Sessions + Inertia + 2 Guards. إضافة JWT تعني إعادة بناء نصف النظام لأسباب لا حاجة لها في Web SaaS. JWT يُفيد فقط للـ Mobile API أو microservices — وكلاهما غير مخطط حالياً.

Session (الحالي) ✓

  • Laravel Sanctum/Guards مدمج
  • CSRF Protection تلقائي
  • No token storage client-side
  • Inertia يعمل بسلاسة معه
  • Revoke فوري (logout = delete session)

JWT (لا نحتاجه الآن) ✗

  • يحتاج Refresh Token logic
  • Storage client-side (localStorage risks)
  • Revoke معقد (blacklist/short TTL)
  • تعارض مع Inertia SPA model
  • Over-engineering للـ Web app
